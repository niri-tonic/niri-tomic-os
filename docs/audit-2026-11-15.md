Initial triage illustrates why upstream language versions need RPM context:

- Pillow CVE-2026-112403 is matched against Python metadata version 12.3.0, but
  installed `python3-pillow-12.3.0-7.fc45` records its backported fix in release -6.
- Certifi GHSA-6q48-6c7w-9gw2 concerns the bundled compromised emSign ECC G3 root.
  The SBOM identifies the system Python package; runtime inspection shows it uses
  Fedora's TLS bundle, where that root is absent.
- Embedded Go module findings also affect binaries such as chezmoi, dsearch,
  Skopeo, Buildah, Podman and Cosign. Those findings need package/upstream-specific
  review; an up-to-date package name alone does not prove a rebuilt dependency.

The raw reports were retained locally under `/tmp/opencode/niri-security/`.
Findings and scanner errors remain advisory under the agreed CI policy; these
observations are not a blanket vulnerability clearance.

## Review findings and decisions

| Location | Finding / consequence | Resolution |
| --- | --- | --- |
| `.github/workflows/build-distro.yml` | Previously published on pushes/nightly without a separate functional qualification gate | Automatic publication retired; manual legacy entrypoint remains until the new release pipeline is qualified |
| `.github/workflows/build-distro.yml` | The former push path filter excluded workflow-only changes | New CI must validate its own changes |
| `.github/workflows/build-iso.yml` | Consumes mutable OS `latest`, not a source-bound digest | Consume the exact qualified OS reference |
| `.github/workflows/build-iso.yml` | Uploads to ttl.sh fail with 502/connection closure | Publish ISO with ORAS to a dedicated GHCR package |
| `.github/workflows/build-iso.yml` / installer v1.4.0 | Fedora 45 run 43711561471 fails before ISO generation: cached Lorax checkout resolves to `git checkout tags/` | Build and qualify an installer runtime with Fedora 45 Lorax sources; a registry change alone cannot fix this |

| Existing installer action | Runs Lorax in a privileged container | User explicitly authorized a narrowly scoped Lorax exception on November 15 |
| Recipe generation | Base resolves to a digest but tool/module tags still float | Retain generated build evidence; track external changes through maintenance |
| `tdesaules/github-actions` | Initial audit found one mixed-event workflow; a parallel update subsequently introduced three entrypoints and per-image qualification | Atomic integration now targets that updated pipeline in a dedicated worktree; new actions still require native qualification and publication |
| Organization credentials | Local API token cannot inspect organization Actions variables/secrets | Verify job-local App token generation on GitHub; never expose secret values |

The user approved explicit releases instead of nightly production publication,
and development/publication of missing actions in `tdesaules/github-actions`.
The Lorax exception does not authorize privileged mode for unrelated actions.
The user separately approved a dedicated BuildKit/socket exception for Atomic

Upstream installer v1.5.0 exists, but its release notes describe the Fedora 44

### Installer prototype result

A local constructor using the pinned v1.5.0 installer sources and Lorax 45.4-1
(matching the available Fedora 45 RPM) successfully produced an AMD64 test ISO.
It embeds a fixture derived from the published OS with an added source-revision
label, not a newly published production release.

- Size: **4,966,055,936 bytes** (4.97 GB / 4.63 GiB).
- SHA-256: `580160dd03da2c7fafe68f506166c02713c474147aa02fa4a0987ecb697796b8`.
- `checkisomd5`: PASS.
- El Torito catalog: bootable BIOS and UEFI entries.
- Volume ID: `niri-x86_64-45`.

This fits the conservative 10 GB GHCR per-layer limit. A disposable QEMU/KVM
guest then installed from this ISO using its extracted kernel/initrd and an
injected test kickstart. The installed disk booted through BIOS, reported Fedora
45.20261115.0, started greetd and a Niri process, and retained the signed update
origin `ghcr.io/niri-tonic/niri-tomic-os:45`. The guest was powered off after its
success marker. No host disk was attached to the VM.

The original ISO also reached the graphical Anaconda welcome screen under OVMF.
A second disposable installation then booted through UEFI, confirmed
`/sys/firmware/efi`, and passed the same greetd/Niri checks. Both test disks were
removed after the guests powered off; logs and the test ISO were retained.

This does not qualify Secure Boot, graphical user login, keyring migration or
physical GPU behavior. Registry upload duration and ORAS round-trip also remain
to validate. No production ISO has been published by this prototype.
